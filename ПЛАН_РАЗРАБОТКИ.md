# План разработки приложения «МедАрхив»

> Кроссплатформенное приложение для сбора, распознавания и каталогизации медицинских документов пользователя: анализов, заключений, описаний исследований, записей о приёмах врача.
>
> **Редакция 2.** Ключевое ограничение: распознавание выполняется **полностью на устройстве**, внешние AI-API и облачные нейросети не используются. Допустимы только узкие локальные модели под конкретную задачу (OCR, классификация, извлечение полей), без генеративного LLM.
>
> Документ рассчитан на исполнение ИИ-агентом (Big Pickle) под контролем человека-ревьюера. Все решения, которые агент не должен принимать самостоятельно, зафиксированы ниже явно.

## 0. Как читать этот документ исполнителю

1. Работать **строго по одной задаче** из раздела 7. Одна задача = одна ветка = один PR.
2. Перед началом задачи прочитать её блок целиком: контекст, файлы, критерии приёмки, команды проверки.
3. Если критерии приёмки недостижимы или противоречат друг другу — **остановиться и задать вопрос**, а не придумывать обходной путь.
4. Не менять стек, версии библиотек, схему БД и публичные API без отдельного ADR (раздел 8.1).
5. Не расширять скоуп задачи. Обнаруженная «попутная» проблема оформляется как issue, а не правится в этом же PR.
6. Реальные персональные и медицинские данные использовать запрещено. Только синтетические фикстуры из `/fixtures`.
7. **Не добавлять сетевые вызовы в контур распознавания.** Любой импорт `http`/`dio` в модулях `features/recognition` — ошибка ревью.
8. Definition of Done — раздел 8.2. PR без выполнения DoD не принимается.

## 1. Продукт

### 1.1 Проблема

Медицинские документы пользователя разбросаны: бумажные фото, PDF из клиник, письма от лабораторий, скриншоты из мессенджеров, файлы в галерее. Найти «тот самый анализ годичной давности» невозможно, динамику показателей не видно, к врачу приходишь без истории.

### 1.2 Решение

Личный медицинский архив:

- **Загрузка** — фото, PDF, DOCX, HEIC и др.
- **Распознавание на устройстве** — OCR + извлечение структурированных сущностей (тип документа, дата, клиника, врач, показатели, диагнозы, препараты). Без интернета и без отправки данных вовне.
- **Каталогизация** — карточки, таймлайн, раздел анализов с динамикой, поиск, теги.
- **Автосбор из почты** — сервер принимает письма, устройство обрабатывает вложения.
- **Автосбор из галереи** — раз в сутки находить новые изображения медицинских документов.

### 1.4 Не-цели MVP (жёстко)

- Постановка диагнозов, рекомендации по лечению, интерпретация анализов «светофором».
- Телемедицина, запись к врачу, чаты с клиниками.
- Интеграция с ЕГИСЗ/ЕМИАС и клиническими системами клиник.
- Социальные функции, публичные профили, шеринг с родственниками.
- Страховые сценарии, ДМС, оплата.
- Веб-версия и десктоп.
- Автоматическая отправка документов кому-либо.
- Любая серверная обработка содержимого документов (OCR, классификация, извлечение).

### 3.3 Модели «одна задача — одна модель»

| Задача | Модель / метод | Размер в приложении | Инференс |
|---|---|---|---|
| Распознавание текста | Tesseract 5, `rus+eng` | ~30 МБ | Нативно, CPU |
| Поиск текстовых блоков и таблиц | Эвристики по bounding boxes + OpenCV | ~5 МБ | Dart/нативно |
| Тип документа | TF-IDF + LogReg (10 классов) | < 1 МБ | Dart |
| Дата, клиника, врач | Regex + словарь клиник + правила контекста | < 2 МБ | Dart |
| Показатели и референсы | Regex + структура таблицы + справочник анализов | ~2 МБ | Dart |
| ФИО и организации (опция) | rubert-tiny2, ONNX | ~30 МБ | ONNX Runtime Mobile |
| Нормализация анализов | Справочник 500 позиций + синонимы | < 1 МБ | Dart |

Правила:
- Модели **версионируются** и указываются в каждом результате (`model_version`).
- Модели поставляются в бандле приложения. Загрузка моделей с сервера — только как обновление и только с нашего домена (C).
- Ни одна модель не делает сетевых запросов.
- Генеративных моделей нет: поля не «сочиняются», только извлекаются. Если не найдено — `null`.

### 3.4 Пайплайн на устройстве

```
Файл → SHA-256 → дедуп?
  → определить MIME (magic bytes)
  → PDF с текстовым слоем: извлечь текст (pdfrx)
  → PDF-скан / изображение: рендер 300 dpi → preprocess (deskew, crop, binarize)
  → DOCX: unzip + parse XML
  → OCR (Tesseract) → слова + bounding boxes + confidence
  → восстановить строки и таблицы по координатам
  → классифицировать тип документа
  → извлечь поля (regex + словари + шаблон лаборатории)
  → валидировать и нормализовать (ISO-даты, единицы, справочник)
  → записать в Drift, построить FTS-индекс
  → статус ready / needs_review
  → синхронизировать оригинал, JSON и превью на сервер
```

Правила:
- Каждый шаг идемпотентен, повторный запуск не создаёт дублей.
- Ошибка шага → повтор до 2 раз, затем `failed` с понятной причиной.
- Файлы > 25 МБ и > 50 страниц — отклоняются с сообщением.
- Обработка по умолчанию: на зарядке и/или при Wi-Fi; иначе — по кнопке.
- Бюджет: ≤ 8 с на страницу на среднем устройстве, пик памяти ≤ 300 МБ.

## 6. Приватность, безопасность, право

### 6.1 Классификация данных

Медицинские данные — специальная категория ПДн (152-ФЗ ст. 10, GDPR ст. 9). Обработка требует **отдельного явного согласия** и повышенных мер защиты.

### 6.2 Что даёт локальное распознавание

- Содержимое документов не передаётся третьим лицам и не уходит в облачные AI-сервисы.
- Распознавание работает в авиарежиме.
- Сервер видит только то, что нужно для синхронизации: оригинал, превью, структурированный JSON.
- Сильный маркетинговый тезис: «Ваши анализы распознаются на телефоне и никуда не отправляются».

Ограничение, которое нужно честно указать в политике: оригиналы и результаты **хранятся на сервере** для синхронизации и восстановления. Полностью zero-knowledge — только в бэклоге (E2E-шифрование).

### 6.3 Обязательные меры MVP

| Мера | Реализация |
|---|---|
| Шифрование в транзите | TLS 1.3, HSTS, certificate pinning |
| Шифрование при хранении | S3 SSE, шифрованный том БД, field-level encryption для токенов почты |
| Доступ к файлам | Только signed URL, TTL ≤ 5 мин, привязка к user_id |
| Аутентификация | JWT 15 мин + refresh 30 дней с ротацией, отзыв по устройству |
| Локальный кэш | SQLCipher, ключ в Keychain/Keystore |
| Логи | Без текста документов, ФИО, значений анализов |
| Телеметрия качества | Только по согласию, без текста документа (только поля и метрики) |
| Аудит | Журнал доступа к документам и экспорту |
| Удаление | Hard delete ≤ 30 дней, каскад в S3, подтверждение в UI |
| Резервные копии | Шифрованные, retention 30 дней, тест восстановления раз в квартал |

### 6.4 Согласия (отдельные чекбоксы, не «пакетом»)

1. Обработка ПДн и медицинских данных.
2. Сканирование почтового ящика.
3. Сканирование галереи.
4. Телеметрия качества распознавания (опционально, по умолчанию выкл.).

Согласий на «облачный OCR/LLM» больше нет — эти функции отсутствуют.

### 6.5 Юридические артефакты до релиза

- Политика конфиденциальности и пользовательское соглашение.
- Уведомление в Роскомнадзор об обработке ПДн.
- Хостинг и первичная обработка ПДн — на серверах в РФ.
- Дисклеймер: приложение не является медицинским изделием, не ставит диагнозы, не заменяет врача.
- Для сторов: Data Safety (Google Play), App Privacy (App Store), обоснование доступа к фото, фоновой активности и локальной обработки.
- Отдельно указать: OCR-модель работает на устройстве, интернет для распознавания не требуется.

### 6.6 Отдельно про почту

**MVP-путь — пересылка на уникальный адрес** (`u-<token>@in.<домен>`): пользователь создаёт правило пересылки в своём ящике. Это:
- работает с Gmail, Outlook, Яндексом, Mail.ru без OAuth;
- не требует verification и CASA-аудита Google (restricted scopes);
- не даёт приложению доступа ко всему ящику — только к пересланным письмам.

Сервер принимает письмо, сохраняет вложения в `inbox_items` и отправляет push. Устройство забирает вложение, распознаёт локально и присылает результат. Если устройство офлайн — вложение ждёт, статус виден в UI.

IMAP и OAuth — следующие фазы. Gmail API с чтением почты требует верификации и ежегодной security-оценки: планировать отдельно, не блокировать MVP.

## 8. Инженерные практики

### 8.1 ADR (Architecture Decision Record)

Каждое необратимое решение — отдельный файл `docs/adr/NNN-название.md`:
контекст → варианты → решение → последствия. Минимум: стек, схема данных, приватность, локальный контур распознавания, выбор OCR-движка, стратегия почты.

### 8.2 Definition of Done (для каждого PR)

- [ ] Код собирается, линтеры и типизация без ошибок.
- [ ] Unit-тесты на новую бизнес-логику; покрытие затронутых модулей ≥ 70 %.
- [ ] Интеграционный тест на новый endpoint или сценарий.
- [ ] Для распознавания — тест на фикстуре с проверкой метрики, а не только «не упало».
- [ ] Проверка отсутствия сетевых вызовов в контуре распознавания.
- [ ] Замер времени и памяти на референсном устройстве (для задач пайплайна).
- [ ] Миграция БД (если нужно) с `upgrade` и `downgrade`.
- [ ] OpenAPI обновлён, клиентский код сгенерирован.
- [ ] Обработка ошибок: понятные коды, без stack trace наружу.
- [ ] Логи без ПДн.
- [ ] Нет секретов в коде и логах.
- [ ] Документация/README обновлены.
- [ ] Для UI — скриншоты (светлая/тёмная тема) в PR.
- [ ] Нет `TODO` в main — только issue.
- [ ] Ручная проверка на эмуляторе/устройстве, включая авиарежим.

### 8.3 Правила для ИИ-исполнителя

1. **Размер задачи:** если дифф > 400 строк или > 8 файлов — разбить на подзадачи и согласовать.
2. **Сначала тест, потом код** — для бизнес-логики (TDD допустим и желателен).
3. **Интерфейсы вместо прямых вызовов:** `OcrEngine`, `DocumentClassifier`, `FieldExtractor`, `StorageProvider`, `MailProvider`. У каждого — `mock`-реализация.
4. **Feature flags** для всего, что включает внешние сервисы (почта, push).
5. **Никаких «умных» догадок в данных:** если поле не найдено — `null`, не заполнять правдоподобным.
6. **Идемпотентность** во всех операциях импорта и синхронизации.
7. **Ошибки внешних API** не должны ронять пайплайн: таймауты, ретраи с jitter.
8. **Локализация:** все строки через ARB, никакого текста в виджетах.
9. **Доступность:** контраст ≥ 4.5:1, тап ≥ 44 pt, семантика для скринридеров.
10. **Коммиты:** Conventional Commits, ветка `feat/T3.4-classifier`.
11. **Не менять фикстуры** без согласования — на них держатся golden-тесты.
12. **Не добавлять зависимости** вне утверждённого списка без ADR.
13. **Не тянуть в приложение облачные SDK** и генеративные модели — это блокирующее нарушение.

## 10. Наблюдаемость и эксплуатация

- **Метрики сервера:** RPS, p95 латентности, размер очереди почты, ошибки синхронизации, размер S3.
- **Метрики клиента (анонимно, по согласию):** время обработки страницы, доля `failed`, доля `needs_review`, распределение типов документов, версии моделей.
- **Логи:** structlog, JSON, корреляция по `request_id` и `document_id`. Без текста документов.
- **Трейсинг:** OpenTelemetry (API + worker).
- **Алерты:** очередь почты > 100, ошибки синхронизации > 5 %, S3 > 80 %, падение crash-free < 99 %.
- **Дашборд качества:** точность по полям и версиям движка, чтобы видеть регресс после обновлений.
- **Бэкапы:** ежедневно, шифрованные, retention 30 дней, ежеквартальный тест восстановления.

### 10.1 Стоимость инфраструктуры

Распознавание локальное, поэтому расходов на AI-API нет. Остаются сервер, БД и объектное хранилище.

| Статья | 1 000 пользователей | 10 000 пользователей |
|---|---|---|
| VPS (API + worker + БД) | 2 500–4 000 ₽/мес | 6 000–10 000 ₽/мес |
| Объектное хранилище (оригиналы + превью) | ~100 ГБ → 250–400 ₽/мес | ~1 ТБ → 2 500–4 000 ₽/мес |
| Бэкапы (+20 %) | ~600 ₽/мес | ~2 000 ₽/мес |
| Домен, TLS, push | ~200 ₽/год | ~200 ₽/год |
| **Итого** | **~3 500–5 000 ₽/мес** | **~11 000–16 000 ₽/мес** |

Допущения: 50 документов на пользователя, средний оригинал 2 МБ, превью 200 КБ.

**Честно про «бесплатно»:**
- Полностью бесплатный вариант — только режим «данные на устройстве», без сервера. Тогда нет почты, бэкапа и мультидевайса.
- Бесплатные тарифы облаков (10–20 ГБ) не подходят: мало места и, как правило, серверы не в РФ (152-ФЗ).
- Снизить стоимость: дедупликация по SHA-256, сжатие превью, холодное хранение оригиналов старше 3 лет, лимит 200 документов на бесплатном тарифе (если появится монетизация).

### 13.2 Осталось уточнить

1. **Приоритет источников:** почта или галерея важнее для первых пользователей? От этого зависит порядок M5/M6 (сейчас почта идёт первой).
2. **Языки:** только русский в MVP или сразу русский + английский?
3. **Шаблоны бланков:** нужны ли в MVP? Это S-задача (T8.3), без неё приложение работает на общих правилах. Если нужны — понадобятся 3–5 обезличенных образцов от вас.

### 13.3 Что такое «шаблон бланка» (пояснение)

Разные лаборатории выдают результаты в разном виде. У «Инвитро», «Гемотеста», «Хеликса», CMD, «ЛабКвеста» свои PDF: где-то таблица слева, где-то справа, где-то дата вверху, где-то в подвале.

**Шаблон бланка** — это заранее размеченная карта конкретного PDF: «здесь дата, здесь название анализа, здесь значение, здесь референс». Приложение сравнивает новый документ с шаблоном и берёт поля из известных мест — точность на таких бланках заметно выше, чем у универсальных правил.

Важно:
- Шаблон не обязателен. MVP извлекает поля общими правилами (regex + координаты + справочник).
- Шаблоны добавляются по реальным обезличенным образцам, которые присылает пользователь с согласия. Ничего не скачивается с сайтов лабораторий.
- Если вы не знаете, какие лаборатории важны, — пропускаем T8.3 и возвращаемся к ней после первых 20–30 пользователей, когда будет видно, какие бланки встречаются чаще.
